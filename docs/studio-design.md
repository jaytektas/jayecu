# jayecu Studio — design

**Status:** built. The studio is `apps/studio-jf`, a C++20 desktop application on **JFramework** (the
same author's toolkit, GPL-3, consumed as an installed SDK). It runs on Linux and Windows; the Windows
build is a MinGW-w64 cross-compile from Linux. It connects to the ECU, reads and writes the tune, shows
live data, edits tables, logs, autotunes, designs trigger wheels, and updates the ECU's firmware.

This document is the map: what the parts are, what each owns, and the contract with the firmware.
The detail lives in each file's own header comment.

## The contract: the meta

The studio knows nothing about any particular firmware at compile time. Everything it needs comes
from **the meta** — `shared/tuneit-meta.json`, generated by `codegen/codegen.py` from
`definition/ecu.schema.yaml` and the board YAML:

- the config layout (every setting's offset, type, scale, limits, units, help, options),
- the telemetry descriptor (how to decode a live 'A' frame into named channels),
- the wire protocol facts (command codes, block size),
- the navigation tree the firmware suggests, the trouble codes, and the shipped trigger-wheel library.

A meta is identified by **board + layout_hash**. The studio keeps a library of them
(`<data>/meta/<board> <layout_hash>.meta`) and, on connect, loads the one matching the hash the ECU
reports. A meta reaches the library four ways: the firmware kits the studio ships with or downloads,
`make codegen` on a development machine, a fetch from the ECU's own SD card (where `make push` puts it),
or an imported TunerStudio `.ini`.

`tests/test_studio_meta_contract.cpp` (in the firmware test suite) runs the studio's real `MetaModel`
reader against the meta codegen just produced, so a codegen change that the studio can no longer read
fails a firmware test.

## Layers

```
apps/studio-jf/
  main.cpp          the shell: window, docks, menus, and the wiring between everything below
  src/comms/        talking to an ECU
  src/model/        the data: meta, value cache, tunes, units, expressions, trigger wheels, autotune
  src/surface/      the dashboard editor/renderer and its widgets
  src/ui/           docks, dialogs and editor views
  src/app/          firmware upgrade and download, desktop integration, help, self-test
  tests/            headless tests (fixtures + golden files); `studio_tests` target, run with ctest
```

**comms** — `EcuLink` speaks the jayecu wire protocol (`OmniFrame`: `[AA 55][type][rsv][len][ts][seq]
[payload][crc16]`, the other end of `firmware/Comms/OmniProtocol.h`). Requests carry a sequence id the
firmware echoes, so they are pipelined and matched to replies, with retry and deadlines. `DeviceScanner`
finds ECUs by polling each jayecu USB port for its identity. `ChunkReader` moves large transfers on a
worker. `Dfu` writes firmware into the STM32's ROM bootloader over USB (the kernel's usbfs directly on
Linux, WinUSB on Windows). `TsLink` + `TsCacheBridge` are interop: they let the same widgets drive an ECU that speaks the
TunerStudio protocol, once its `.ini` has been imported.

**model** — `MetaModel` is the loaded meta. `Cache` is the value store between comms and widgets: the
link hands it raw frames and config images, it decodes them through the meta into named values, and
widgets read from it; edits go back out through it with undo. `TuneFile` is the `.tune` format
(`jayecu-tune/2`: named fields, raw values, the layout_hash it was saved against) and migrates a tune
across a layout change, reporting what did not carry over. `Ecu` is the per-ECU store. `UnitManager`
handles display units, `ExprCompiler` compiles the expressions the firmware's expression VM runs
(sharing `firmware/Signal/ExprIsa.h`), and `Autotune` is the VE autotuner's arithmetic.

**surface** — a dashboard is a set of **surfaces** (tabs). Each surface is a `PanelModel`: a virtual
canvas and a flat list of widget instances, each a type key, a rect and a property bag. The model is
the truth; `Surface` renders it and, in edit mode, authors it. Every navigation-tree node owns one page
(`PanelLibrary`), which can be placed on many surfaces as a viewport. Widgets register themselves
(`REGISTER_WIDGET`), so adding one touches only its own files.

**ui** — the navigation tree, the dictionary of settings and channels, the trouble-code and diagnostics
docks, the trigger designer (`docs/trigger-designer-design.md`), trigger log and engine-cycle views,
knock scope, autotune view, and the dialogs (output wizard, CAN templates, preferences, tune diff, …).

**app** — `FirmwareUpgrade` puts a firmware kit on the ECU and brings the tune across by name, first
installing the USB permission it needs if missing (on Linux the udev rule from
`tools/udev/70-jayecu.rules`, read in at build time; on Windows the WinUSB driver, through libwdi).
`FirmwareFetch` downloads newer kits. `DesktopIntegration` offers to add the AppImage to the desktop's
application menu.

## On disk

Everything the studio writes lives under one data root — `~/.local/share/jayecu/jayecu Studio` on
Linux, `%APPDATA%` on Windows — answered in one place (`StudioPaths`):

```
meta/           the meta library, "<board> <layout_hash>.meta"
ecus/<uid>/     one folder per ECU, keyed by its factory UID:
                  ecu.json, tunes/<name>.tune, dashboard.gui, restore/ (connect-time snapshots)
dashboards/     board dashboards, installed from kits or by `make dash`
firmware/       downloaded firmware kits
can_templates/  CAN device templates
calibrations/   sensor calibrations
datalogs/       recorded logs
ini/            imported .ini files
trigger_wheels.json   the user's own wheels
```

A **dashboard** (`dashboard.gui`) is one document: the navigation tree, the surfaces and the page
library together. The board's authored dashboard is `definition/boards/<board>.dashboard.gui`; it ships
in the firmware kit and is pushed to the ECU's SD card, so a studio installed from a release still has it
on the first connect.

## Firmware kits and updates

A **kit** is one firmware build's image, meta and dashboard, with a `kit.json` naming them
(`tools/make_kit.py`, `make kit`). The studio ships with the newest kit and can download newer ones
from the project's releases. Updating an ECU: read the tune off it, show what the new firmware drops and
adds, check ignition off and engine stopped, flash over DFU, then write the tune back by name. The
firmware states the oldest studio it works with (`firmware/min_studio.txt`), carried in the kit.

## Principles

1. **The meta is the only description of the firmware.** The studio never hard-codes an offset, a
   field list or a protocol constant that the meta can carry.
2. **Model is truth.** Surfaces, the tree and the tune are data; views are projections of it.
3. **Writes are deliberate.** Edits go to the ECU's RAM as they are made; committing them to flash is
   the Burn button and nothing else.
4. **No backwards compatibility** while nothing is released: firmware and studio change together.

## Building

```
make studio            # apps/studio-jf/build/studio
make studio-win        # apps/studio-jf/build-win/studio.exe
make studio-appimage   # Linux package
make studio-installer  # Windows installer (Inno Setup)
cmake --build apps/studio-jf/build --target studio_tests && ctest --test-dir apps/studio-jf/build
```
